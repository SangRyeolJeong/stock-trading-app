# 금융 백엔드 학습·구현 계획

## 1. 목표

이 프로젝트의 목표는 단순히 주식매매 기능을 많이 구현하는 것이 아니다.
실제 금융 백엔드에서 발생할 수 있는 데이터 정합성 문제를 공부하고, 다음 흐름을
코드와 문서, 자동화된 테스트로 증명하는 것을 목표로 한다.

```text
문제 상황
→ 실패 재현
→ 관련 이론 정리
→ 설계 선택지 비교
→ 선택한 방식과 이유 기록
→ 코드 구현
→ 정상·실패·동시성 테스트
→ 현재 구현의 한계 기록
```

최종적으로 저장소만 읽어도 다음 내용을 설명할 수 있어야 한다.

- 주문 처리 중 서버가 죽어도 부분 데이터가 남지 않는 이유
- 중복 요청과 동시 요청이 중복 체결이나 초과 지출로 이어지지 않는 이유
- 주문, 체결, 현금 원장, 포지션이 서로 일치하는지 검증하는 방법
- DB 트랜잭션으로 되돌릴 수 없는 외부 증권사 주문을 복구하는 방법
- 선택한 설계의 장점뿐 아니라 단점과 변경이 필요한 조건

## 2. 현재 구현과 검증 공백

현재 모의 주문 시스템에는 다음 기반이 구현되어 있다.

- SQLAlchemy `async with session.begin()`을 이용한 트랜잭션
- 계좌와 포지션에 대한 `SELECT ... FOR UPDATE` 잠금
- 계좌별 멱등성 키 유일 제약
- 주문, 체결, 현금 원장, 포지션, 포트폴리오 스냅샷 저장
- 현금 부족과 보유 수량 부족 검증
- PostgreSQL을 실행하는 CI 작업

다만 다음 항목은 추가 구현과 증명이 필요하다.

- 처리 단계별 장애가 발생했을 때 전체 롤백되는지 검증하는 테스트
- SQLite가 아닌 PostgreSQL에서 수행하는 실제 행 잠금 및 동시성 테스트
- 원장을 수정할 수 없도록 하는 append-only 정책
- 원장, 체결, 포지션 사이의 불일치를 탐지하는 대사 기능
- 여러 메서드에 흩어진 주문 상태 전이를 통제하는 상태 머신
- 시세 서비스 장애 중에도 완료된 주문을 재조회할 수 있는 멱등성 처리
- 실제 증권사 주문과 로컬 DB 사이의 분산 트랜잭션 대응

## 3. 공통 산출물

각 학습 주제는 가능한 한 다음 산출물을 하나의 변경 묶음으로 남긴다.

- `docs/backend-learning/`: 개념, 장애 시나리오, 실험 결과와 한계
- `docs/adr/`: 선택지, 결정, 근거와 트레이드오프
- 서비스 및 도메인 코드
- 정상 경로 테스트
- 예외와 장애 주입 테스트
- PostgreSQL 동시성 테스트가 필요한 경우 별도 통합 테스트
- CI 검증 단계

ADR은 최소한 다음 항목을 포함한다.

1. 해결하려는 문제
2. 고려한 선택지
3. 최종 선택
4. 선택한 이유
5. 장점과 단점
6. 나중에 설계를 변경해야 할 조건

구현 과정에서는 PostgreSQL, SQLAlchemy 등 사용 기술의 공식 문서를 우선하여
참고하고 학습 문서에 출처를 기록한다.

## 4. 단계별 계획

### 4.1 주문 체결의 원자성과 롤백

#### 학습 질문

- 트랜잭션은 어디서 시작하고 끝나야 하는가?
- SQLAlchemy의 `flush()`와 `commit()`은 어떻게 다른가?
- ORM 객체를 변경한 후 예외가 발생하면 DB 상태도 원상 복구되는가?
- 예상된 비즈니스 실패와 예상하지 못한 시스템 장애를 어떻게 구분하는가?
- 외부 시세 조회를 DB 트랜잭션 안에 넣으면 어떤 문제가 생기는가?

현재 외부 시세 조회는 DB 트랜잭션 바깥에서 수행된다. 네트워크 응답을 기다리는
동안 계좌 잠금을 점유하지 않는다는 장점이 있으므로 이 경계는 유지한다.

#### 구현

현재 `_settle_order()`에 모인 작업을 의미 있는 내부 단계로 분리한다.

```text
주문 생성
→ 주문 가능 자원 검증
→ 포지션 변경
→ 체결 기록
→ 매매대금 원장 기록
→ 수수료 원장 기록
→ 포트폴리오 스냅샷 기록
```

내부 단계는 분리하지만 각각 커밋하지 않는다. 공개 서비스 메서드 하나가 전체
트랜잭션을 소유하며, 모든 DB 변경은 하나의 원자적 작업으로 처리한다.

운영 코드에 장애 발생용 환경변수나 API를 추가하지 않는다. 테스트에서 내부 단계
메서드를 monkeypatch하여 예외를 발생시키는 방식으로 장애를 주입한다.

#### 장애 주입 테스트

다음 지점마다 의도적인 예외를 발생시킨다.

- 주문 행 생성 직후
- 포지션 변경 직후
- 체결 저장 직후
- 매매대금 원장 저장 직후
- 수수료 원장 저장 직후
- 포트폴리오 스냅샷 저장 직전

각 테스트는 장애 전후의 다음 상태가 완전히 같은지 검증한다.

- 주문 수
- 체결 수
- 현금 원장 행 수와 금액 합계
- 통화별 현금 잔액
- 포지션 수량, 평균단가와 실현손익
- 포트폴리오 스냅샷 수

롤백된 멱등성 키로 같은 주문을 다시 요청하면 정상적으로 성공해야 한다. 실패한
주문 행이 남아 재시도를 방해하지 않는다는 점까지 증명한다.

지정가 주문 체결 시점에 현금이나 보유 수량이 부족한 경우는 시스템 장애와 다르게
처리한다. 이는 정상적인 비즈니스 결과이므로 주문을 `rejected`로 전환하고 해당
상태를 커밋한다.

#### 완료 기준

- 모든 장애 지점에서 부분 데이터가 남지 않는다.
- 정상 주문 결과와 기존 API 계약이 유지된다.
- 실패한 주문을 동일 멱등성 키로 안전하게 재시도할 수 있다.
- 트랜잭션 경계와 예외 처리 정책을 ADR로 기록한다.
- SQLite 테스트로 증명할 수 없는 범위를 문서에 명시한다.

### 4.2 PostgreSQL 동시 주문과 행 잠금

#### 학습 질문

- 두 요청이 같은 잔액을 동시에 읽으면 어떤 문제가 발생하는가?
- Lost Update와 Write Skew는 무엇인가?
- PostgreSQL 기본 `READ COMMITTED` 격리 수준에서 `FOR UPDATE`는 어떻게 동작하는가?
- 계좌 전체 잠금과 종목별 잠금은 어떤 차이가 있는가?
- SQLite 테스트만으로 행 잠금을 검증할 수 없는 이유는 무엇인가?

현재 구현은 계좌 행을 먼저 잠가 동일 계좌의 주문을 직렬화한다. 처리량 측면에서는
거친 잠금이지만 모의투자 단계에서는 이해하기 쉽고 정확성을 우선하는 선택이다.

#### PostgreSQL 테스트 환경

- `backend/tests/postgres/`에 PostgreSQL 전용 테스트를 분리한다.
- 두 개 이상의 독립적인 `AsyncSession`으로 실제 경쟁을 만든다.
- 테스트가 `Base.metadata.create_all()`에 의존하지 않고 Alembic으로 생성한 스키마를 사용하게 한다.
- CI에서 PostgreSQL 기동, 마이그레이션, 동시성 테스트, 불변식 검사를 순서대로 실행한다.

#### 동시성 시나리오

- 한 주문만 살 수 있는 현금으로 매수 두 건을 동시에 요청한다.
- 한 번만 팔 수 있는 포지션으로 매도 두 건을 동시에 요청한다.
- 동일 멱등성 키를 가진 주문 두 건을 동시에 요청한다.
- 지정가 주문의 체결과 취소를 동시에 요청한다.
- 신규 사용자의 첫 계좌 요청을 동시에 실행한다.

#### 완료 기준

- 현금 잔액과 포지션 수량이 음수가 되지 않는다.
- 동일 주문이 두 번 체결되지 않는다.
- 체결과 취소가 동시에 성공하지 않는다.
- 초기 입금 원장이 중복 생성되지 않는다.
- 모든 동시성 테스트 후에도 원장 불변식이 유지된다.

### 4.3 멱등성과 네트워크 재시도

#### 장애 시나리오

서버가 주문을 정상적으로 커밋했지만 응답을 반환하기 전에 연결이 끊길 수 있다.
클라이언트는 실패했다고 판단하고 동일 주문을 재전송한다.

현재 DB 유일 제약은 중복 체결을 막지만, 기존 주문을 확인하기 전에 외부 시세부터
조회한다. 따라서 이미 완료된 주문의 재시도가 시세 서비스 장애 때문에 실패할 수
있다.

#### 구현

- 요청 내용을 정규화한 fingerprint를 저장한다.
- 멱등성 키와 fingerprint를 함께 비교한다.
- 기존 주문 조회를 외부 시세 조회보다 먼저 수행한다.
- 기존 주문이 있으면 시세 API를 호출하지 않고 저장된 결과를 반환한다.
- 기존 주문이 없을 때만 시세를 조회한다.
- 시세 조회 후 실제 주문 트랜잭션 안에서 멱등성을 다시 확인한다.
- 계좌와 멱등성 키의 DB 유일 제약을 최종 방어선으로 유지한다.
- 같은 키를 다른 요청 내용에 사용하면 `409 Conflict`를 반환한다.

트랜잭션 전의 첫 조회와 실제 저장 사이에는 경쟁 조건이 있으므로 두 번째 확인을
생략하지 않는다.

#### 테스트

- 성공 후 응답 유실을 가정한 재시도
- 시세 서비스 장애 중 완료된 주문 재조회
- 동일 키와 동일 요청의 동시 호출
- 동일 키와 다른 수량의 호출
- 첫 요청 롤백 후 동일 키 재사용
- 중복 주문, 체결, 원장 기록이 발생하지 않는지 확인

### 4.4 원장 불변식과 대사

현재 현금은 원장 `amount`의 합계로 계산하지만 각 행에 `balance_after`도 저장한다.
조회와 감사에는 편리하지만 두 값이 불일치할 수 있다는 트레이드오프가 있다.

#### 구현

읽기 전용 `PaperLedgerReconciler`와 다음 CLI를 추가한다.

```bash
python -m app.cli.reconcile_paper_ledger
```

대사기는 다음 불변식을 검사한다.

- `filled` 주문은 정확히 하나의 체결을 가진다.
- 미체결 주문은 체결을 가지지 않는다.
- 매수 원장 금액은 `-gross_amount`이다.
- 매도 원장 금액은 `+gross_amount`이다.
- 수수료 원장 금액은 `-fee`이다.
- 현재 잔액은 모든 현금 원장 금액의 합과 같다.
- 최근 `balance_after`는 원장 누적 합계와 같다.
- 포지션 수량은 매수 체결 합계에서 매도 체결 합계를 뺀 값이다.
- 포지션 수량은 음수가 될 수 없다.
- 한 주문에 필요한 원장 행이 누락되거나 중복되지 않는다.

정상 상태에서는 성공 종료 코드를 반환한다. 불일치가 있으면 계좌, 통화, 주문
단위로 문제를 출력하고 실패 종료 코드를 반환한다.

#### Append-only 정책

- 애플리케이션에 원장 수정 및 삭제 기능을 만들지 않는다.
- PostgreSQL trigger, DB 권한 분리, 애플리케이션 규칙을 비교하여 ADR로 남긴다.
- 잘못된 원장은 기존 행을 수정하지 않고 반대 금액의 조정 원장을 추가한다.
- 테스트 데이터에 의도적인 불일치를 만든 뒤 대사기가 이를 탐지하는지 검증한다.

### 4.5 주문 상태 머신과 감사 이력

주문 상태 변경 규칙을 하나의 도메인 상태 머신으로 모은다.

```text
accepted ──→ filled
    ├──────→ cancelled
    └──────→ rejected

filled / cancelled / rejected = 종료 상태
```

#### 구현

- 허용 상태와 상태 전이 규칙을 명시한다.
- 잘못된 상태 전이에 전용 도메인 예외를 발생시킨다.
- DB `CHECK` 제약으로 정의되지 않은 상태를 차단한다.
- `order_status_events` 감사 테이블을 추가한다.
- 이전 상태, 새 상태, 변경 이유와 변경 시각을 기록한다.
- 주문 생성부터 종료까지 상태 이력을 조회할 수 있게 한다.

#### 테스트

- 체결 주문 취소 금지
- 취소 주문 재체결 금지
- 거절 주문 재체결 금지
- 동일 취소 요청의 안전한 반복 처리
- 체결과 취소의 동시 실행
- 현재 주문 상태와 마지막 상태 이벤트의 일치

### 4.6 교착 상태와 트랜잭션 재시도

모든 예외를 무조건 재시도하지 않고 PostgreSQL 오류의 의미에 따라 분류한다.

재시도를 고려할 오류는 다음과 같다.

- deadlock detected
- serialization failure
- 안전성이 확인된 일시적인 DB 연결 오류

다음 오류는 재시도하지 않는다.

- 현금 부족
- 보유 수량 부족
- 멱등성 충돌
- 입력 검증 오류
- 외부 주문이 이미 전송됐을 가능성이 있는 작업

재시도 횟수에 상한을 두고 jitter를 적용한다. 시도 횟수와 최종 실패 원인을
구조화 로그와 메트릭으로 남긴다.

### 4.7 실제 증권사 주문과 Transactional Outbox

#### 해결할 문제

다음 두 작업은 하나의 DB 트랜잭션으로 묶을 수 없다.

```text
우리 DB에 주문 저장
증권사 API에 주문 전송
```

증권사 주문이 접수된 직후 서버가 중단되면 로컬 DB에는 실패처럼 보이지만 실제
주문은 유효할 수 있다. 이 문제는 DB 롤백으로 해결하지 않는다.

#### 구현 구조

```text
API 요청
→ DB 트랜잭션
   ├─ 주문을 pending_submission 상태로 저장
   └─ outbox 이벤트 저장
→ 커밋
→ worker가 outbox 이벤트 조회
→ 증권사 API 전송
→ 전송 결과 저장
→ 미확정 주문은 증권사 API와 대사
```

다음 정보를 영속화한다.

- outbox event ID
- client order ID
- 증권사 주문 ID
- 전송 시도 횟수
- 다음 재시도 시각
- 마지막 오류
- 전송 및 대사 상태

worker는 `FOR UPDATE SKIP LOCKED`를 사용해 여러 인스턴스가 같은 이벤트를 동시에
처리하지 않게 한다. 다만 잠금만으로 네트워크 요청의 exactly-once 처리를 보장할 수
없으므로 client order ID, 증권사 주문 조회와 대사를 함께 사용한다.

취소 요청은 원상 복구가 보장되는 롤백이 아니라 성공 여부를 확인해야 하는
best-effort 보상 작업으로 취급한다.

실제 KIS 매매 API를 연결하기 전 `FakeBrokerGateway`로 다음 상황을 검증한다.

- DB 커밋 전 장애
- 커밋 후 worker 실행 전 장애
- 증권사 접수 후 응답 유실
- worker 중복 실행
- 증권사 API 타임아웃
- 재조회 과정에서 기존 주문 발견
- 취소 요청 실패와 후속 대사

## 5. 구현 순서와 커밋 단위

첫 번째 마일스톤은 주문 백엔드의 기초를 증명하는 다음 세 단계로 묶는다.

1. 주문 체결 원자성과 롤백
2. PostgreSQL 동시성과 행 잠금
3. 멱등성과 안전한 재시도

권장 커밋 단위는 다음과 같다.

```text
test: prove atomic rollback during order settlement
docs: explain order transaction boundaries
test: verify order locking on PostgreSQL
docs: document concurrency and locking tradeoffs
feat: make order retries independent from market data
docs: record idempotency design and failure cases
feat: add paper ledger reconciliation
feat: enforce auditable order state transitions
feat: add transactional outbox for broker orders
```

문서와 코드가 같은 학습 주제를 설명한다면 하나의 커밋으로 묶을 수 있다. 변경이
큰 경우에는 실패 테스트를 먼저 커밋하고 구현 커밋에서 테스트를 통과시키는 방식도
사용한다.

## 6. 전체 완료 기준

다음 질문에 문서와 자동화 테스트로 답할 수 있을 때 이 계획을 완료한 것으로 본다.

- 주문 처리 중 서버가 중단되면 부분 데이터가 남는가?
- 동일 주문을 두 번 보내면 두 번 체결되는가?
- 동시에 매수하면 잔고보다 많은 금액을 사용할 수 있는가?
- 체결과 취소가 경쟁하면 최종 상태는 어떻게 결정되는가?
- 원장과 포지션이 어긋났는지 어떻게 발견하는가?
- 잘못 기록된 원장을 기존 데이터 수정 없이 어떻게 보정하는가?
- 어떤 DB 오류를 재시도하고 어떤 오류는 재시도하면 안 되는가?
- DB 작업과 증권사 API 호출 사이의 장애를 어떻게 복구하는가?
