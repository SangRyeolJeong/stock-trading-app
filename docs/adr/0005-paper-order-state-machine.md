# ADR 0005: 감사 가능한 모의주문 상태 전이

- 상태: 채택
- 결정일: 2026-09-01

## 해결하려는 문제

주문 상태 변경이 생성·체결·취소·거절 경로에 흩어져 있으면 종료된 주문을 다시
체결하거나, 현재 상태만 바뀌고 변경 근거가 남지 않는 결함이 생길 수 있다. 문자열
컬럼만으로는 잘못된 상태 값도 DB가 거부하지 못한다.

## 고려한 선택지

### 서비스별 조건문 유지

변경량은 작지만 새 쓰기 경로마다 규칙과 감사 기록을 반복해야 한다. 규칙 누락을
컴파일이나 DB가 발견하지 못한다.

### 상태 전용 라이브러리 사용

복잡한 분기, 가드와 콜백에는 유용하지만 현재 그래프는 활성 상태 하나와 종료 상태
세 개뿐이다. 의존성과 추상화 비용이 현재 문제보다 크다.

### 작은 도메인 상태 머신과 append-only 이벤트 테이블

허용 전이를 한 모듈에 명시하고 주문 상태 변경과 이벤트 추가를 같은 트랜잭션에서
처리한다. DB `CHECK` 제약은 정의되지 않은 상태와 이벤트 전이를 차단한다.

## 최종 선택

세 번째 방식을 채택한다.

- 주문은 항상 `accepted`로 생성한다.
- `accepted`에서만 `filled`, `cancelled`, `rejected`로 전이할 수 있다.
- 세 종료 상태에서는 추가 전이를 허용하지 않는다.
- 생성은 sequence 1, 종료 전이는 sequence 2로 기록한다.
- 동일 취소 재요청은 기존 결과를 반환하고 이벤트를 추가하지 않는다.
- 기존 주문은 migration에서 생성 이벤트와 필요한 종료 이벤트를 역채운다.

sequence는 UUID와 동일한 DB 시각이 쓰기 순서를 표현하지 못하는 문제를 피한다.
현재 상태 그래프에서는 주문당 최대 두 이벤트지만, 이후 부분 체결이나 외부 증권사
상태를 도입하면 sequence 할당 전략과 전이 그래프를 확장해야 한다.

## 장점과 단점

장점:

- 모든 정상 상태 변경이 하나의 규칙과 감사 쓰기 경로를 사용한다.
- 주문 상태와 이벤트는 함께 커밋되거나 함께 롤백된다.
- API와 대사기로 생성부터 종료까지의 근거를 확인할 수 있다.
- 애플리케이션 누락 일부를 DB 제약이 다시 차단한다.

단점:

- DB를 직접 수정하면 주문 상태와 마지막 이벤트가 어긋날 수 있어 대사가 필요하다.
- migration 이전의 정확한 종료 시각과 사유는 알 수 없어 `migration_backfill`로
  표시한다.
- 현재 고정 sequence 1/2 구조는 다단계 주문 상태에 그대로 사용할 수 없다.

## 변경이 필요한 조건

부분 체결, 정정, 만료, 증권사 제출·확인 상태를 추가하거나 한 주문에 반복 전이가
필요해지면 계좌 잠금 아래에서 다음 sequence를 할당하고 낙관적 버전 또는 별도
sequence 생성 규칙을 도입한다. 외부 시스템 사실을 기록할 때는 본 상태 이벤트만
으로 exactly-once를 주장하지 않고 outbox와 증권사 대사를 함께 사용한다.
