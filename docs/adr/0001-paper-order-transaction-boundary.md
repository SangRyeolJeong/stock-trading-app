# ADR 0001: 모의 주문 체결 트랜잭션 경계

- 상태: 채택
- 결정일: 2026-08-12

## 해결하려는 문제

모의 주문 한 건을 체결하면 주문, 포지션, 체결, 매매대금 원장, 수수료 원장과
포트폴리오 스냅샷이 함께 변경된다. 중간 단계에서 예상하지 못한 예외가 발생해도
일부 행만 남지 않아야 한다. 반면 시세 조회처럼 응답 시간이 불확실한 외부 호출을
트랜잭션에 포함하면 계좌 잠금과 DB 연결을 불필요하게 오래 점유한다.

또한 시스템 장애와 주문 가능 자원 부족은 결과가 다르다. 전자는 전체 작업을
되돌려 안전한 재시도를 허용해야 하고, 대기 주문 체결 시점의 현금·수량 부족은
정상적인 비즈니스 결과인 `rejected`로 기록해야 한다.

## 고려한 선택지

### 단계마다 커밋

각 행을 저장한 직후 커밋하면 구현 흐름은 눈에 보이지만 후속 단계 실패 시 이미
커밋된 포지션이나 원장을 자동으로 되돌릴 수 없다. 복구용 보상 로직이 필요하고
그 보상 자체도 실패할 수 있다.

### 시세 조회를 포함한 하나의 트랜잭션

외부 시세 응답과 DB 변경을 한 서비스 호출에 둘 수 있지만 네트워크 대기 중에도
트랜잭션, DB 연결과 계좌 행 잠금을 유지한다. 외부 시스템 응답은 DB 롤백의
대상도 아니다.

### 시세 조회 후 하나의 DB 트랜잭션

시세는 트랜잭션 밖에서 조회하고, 주문에 필요한 모든 DB 변경만 하나의
`session.begin()` 범위에서 처리한다. 내부 단계는 메서드로 나누되 커밋하지 않는다.

## 최종 선택

시세 조회 후 하나의 DB 트랜잭션을 사용한다.

- API 계층은 먼저 시세를 조회한다.
- 공개 주문 서비스 메서드가 `async with session.begin()`으로 트랜잭션을 소유한다.
- 계좌 확인과 잠금, 종목 저장, 주문 생성, 자원 검증, 포지션 변경, 체결, 두 원장
  행과 스냅샷 저장을 같은 트랜잭션에 둔다.
- 내부 단계는 `_create_order()`, `_apply_position_change()`,
  `_record_execution()`, `_record_trade_settlement()`, `_record_commission()`,
  `_record_portfolio_snapshot()`으로 구분한다.
- 내부 단계는 `commit()`하지 않는다. `flush()`는 SQL을 현재 트랜잭션에 보내는
  동작일 뿐 성공을 확정하는 경계로 취급하지 않는다.
- 예상하지 못한 예외는 잡지 않고 트랜잭션 소유자까지 전파하여 전체 롤백한다.
- 대기 주문 체결 시 `InsufficientCashError` 또는 `InsufficientPositionError`가
  발생하면 주문만 `rejected`로 바꾸고 정상적으로 커밋한다.
- 운영 코드에는 장애 주입 환경변수나 API를 두지 않는다. 테스트가 내부 단계만
  monkeypatch하고, 예외 직전 `flush()`하여 DB에 전달된 변경도 롤백되는지 확인한다.

## 선택한 이유

주문 체결은 여러 테이블을 함께 바꾸는 하나의 논리적 작업이다. PostgreSQL은 한
트랜잭션에 포함된 여러 변경을 전부 적용하거나 전부 취소한다. SQLAlchemy의
`Session.begin()` 컨텍스트도 정상 종료 시 커밋하고 예외 시 롤백하는 경계를
제공한다. 따라서 애플리케이션 보상 로직 없이 DB 변경의 원자성을 유지할 수 있다.

시세 조회를 먼저 끝내면 네트워크 대기 시간을 DB 트랜잭션에서 제거할 수 있다.
이는 시세와 체결 사이에 시간 차이가 존재한다는 단점이 있지만, 현재 모의 주문의
시세 스냅샷 정책과 일치한다.

## 장점과 단점

장점:

- 장애 지점과 관계없이 부분 주문, 체결, 원장, 포지션과 스냅샷이 남지 않는다.
- 롤백된 멱등성 키는 새 요청에서 다시 사용할 수 있다.
- 각 저장 단계의 책임이 분리되어 장애 주입과 단위 검증이 가능하다.
- 외부 시세 지연이 DB 트랜잭션 시간을 늘리지 않는다.

단점:

- 시세 조회 시점과 계좌 잠금·체결 시점 사이에 가격의 시간 차이가 있다.
- SQLite 장애 주입 테스트는 ORM 트랜잭션 롤백을 증명하지만 PostgreSQL 행 잠금,
  격리 수준과 프로세스 중단 내구성까지 증명하지 않는다.
- 즉시 체결 주문은 기존 API 동작을 보존하기 위해 현재 생성 시점부터 `filled`
  상태를 사용한다. `accepted → filled` 감사 전이는 주문 상태 머신 단계에서
  정규화해야 한다.

## 나중에 설계를 변경해야 할 조건

- 실제 증권사 주문을 전송할 때는 외부 API를 이 트랜잭션에 넣지 않고 별도 주문
  모델과 transactional outbox를 사용한다.
- 종목별 병렬 처리량이 중요해지면 계좌 전체 잠금 대신 현금 버킷·포지션별 잠금과
  예약 모델을 검토한다.
- 지정가 주문이 백그라운드 체결기로 이동하면 같은 트랜잭션 정책과 잠금 순서를
  worker 진입점에도 적용한다.
- 시세 유효 기간이나 허용 slippage가 제품 요구사항이 되면 트랜잭션 진입 전후의
  시세 검증 정책을 별도로 추가한다.
