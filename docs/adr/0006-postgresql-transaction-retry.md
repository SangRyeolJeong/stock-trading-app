# ADR 0006: PostgreSQL 주문 트랜잭션의 제한적 재시도

- 상태: 채택
- 결정일: 2026-09-06

## 해결하려는 문제

동시 주문이 여러 행을 잠그면 PostgreSQL이 교착 상태의 한 트랜잭션을 중단하거나,
직렬화 가능한 격리 수준에서 직렬화 실패를 반환할 수 있다. 이런 실패를 그대로
사용자에게 돌려주면 안전하게 다시 실행할 수 있는 주문도 불필요하게 실패한다.
반대로 모든 DB·비즈니스 오류를 재시도하면 중복 부작용, 지연 증가와 장애 증폭을
만들 수 있다.

## 고려한 선택지

### 모든 예외 재시도

일시 오류를 폭넓게 흡수하지만 입력 오류, 현금 부족과 멱등성 충돌도 반복한다.
커밋 결과가 불확실한 연결 단절까지 재실행하면 외부 부작용이 있는 작업에서는 특히
위험하다.

### SQL 문장 하나만 재시도

변경량은 작지만 앞선 조회와 판단이 이미 무효가 됐을 수 있다. PostgreSQL은
직렬화 실패 시 값을 결정하는 로직을 포함한 전체 트랜잭션 재시도를 요구한다.

### 명시적인 SQLSTATE만 전체 트랜잭션 재시도

DB가 트랜잭션을 중단한 의미가 분명한 오류만 분류하고, 트랜잭션 소유 메서드
전체를 다시 호출한다. 재시도 횟수와 지연에 상한을 둔다.

## 최종 선택

세 번째 방식을 채택한다.

- `40P01` (`deadlock_detected`)과 `40001` (`serialization_failure`)만 재시도한다.
- 주문 생성, 대기 주문 체결, 취소의 `session.begin()` 전체 범위를 다시 실행한다.
- 최초 시도를 포함해 기본 3회로 제한한다.
- 지연 상한을 지수적으로 늘리고 `0..상한`의 full jitter를 적용한다.
- 재시도와 최종 소진을 사유별 카운터 및 구조화된 `LogRecord` 필드로 기록한다.
- 현금·수량 부족, 멱등성 충돌, 입력 검증 오류는 즉시 반환한다.
- SQLSTATE `08` 계열 연결 오류는 커밋 성공 여부가 불확실할 수 있어 제외한다.
- 외부 증권사 전송을 포함하는 메서드에는 이 decorator를 적용하지 않는다.

설정 기본값은 3회, 10ms base, 250ms 최대 지연이다. 최대 지연은 base보다 작을 수
없으며 환경변수에도 안전한 상한을 둔다.

## 장점과 단점

장점:

- PostgreSQL이 명시적으로 중단한 트랜잭션을 처음부터 다시 판단한다.
- 제한과 jitter가 동시 재시도의 재충돌과 DB 부하를 줄인다.
- 비즈니스 실패의 응답 의미와 지연을 바꾸지 않는다.
- 사유·시도·지연과 최종 소진을 로그와 카운터로 구분한다.

단점:

- 프로세스 로컬 카운터는 인스턴스 재시작 시 초기화되고 아직 외부 메트릭
  시스템으로 export되지 않는다.
- PostgreSQL 통합 테스트를 실행하지 않는 기본 SQLite 테스트에서는 실제 DB의
  교착 감지까지 증명하지 못한다.
- 연결 오류 중 안전하게 재시도 가능한 일부 상황도 보수적으로 실패 처리한다.

## 변경이 필요한 조건

Prometheus나 OpenTelemetry를 도입하면 현재 카운터를 공식 exporter로 교체한다.
연결 오류 재시도가 필요하면 커밋 단계별 결과 불확실성을 먼저 분류하고 주문
멱등성·대사와 결합한다. 실제 증권사 호출은 transactional outbox로 분리한 뒤
worker의 전송 상태에 맞는 별도 정책을 사용한다.
