# ADR 0002: 모의 주문의 계좌 단위 비관적 잠금

- 상태: 채택
- 결정일: 2026-08-12

## 해결하려는 문제

PostgreSQL 기본 `READ COMMITTED` 격리 수준에서 두 트랜잭션은 같은 시점의 현금
원장 합계나 포지션을 읽고 각각 주문 가능하다고 판단할 수 있다. 두 요청이 모두
체결되면 현금 초과 지출, 보유 수량 초과 매도, 중복 체결이나 체결·취소의 동시
성공이 발생할 수 있다.

애플리케이션의 모든 주문 변경 경로가 같은 잠금 대상을 같은 순서로 획득해야 한다.
일부 경로만 계좌를 잠그거나 join된 여러 테이블을 한 번에 잠그면 직렬화 전제가
깨지고 교착 상태 또는 PostgreSQL의 outer join 잠금 오류가 생길 수 있다.

## 고려한 선택지

### 잠금 없이 `READ COMMITTED`만 사용

일반 조회는 각 SQL 문 시작 시점의 스냅샷을 본다. 현금 잔액처럼 여러 원장 행의
집계 결과는 그 자체로 잠글 행이 없으므로 두 요청이 같은 가용 현금을 사용할 수
있다.

### `SERIALIZABLE` 격리와 트랜잭션 재시도

가장 강한 격리로 직렬 실행과 같은 결과를 목표로 할 수 있지만 serialization
failure를 정상적으로 재시도하는 기반이 먼저 필요하다. 현재 학습 단계에는 오류
분류와 재시도 정책이 아직 없다.

### 종목·통화별 세밀한 잠금과 예약 테이블

서로 독립적인 종목이나 통화 주문의 병렬성을 높일 수 있다. 대신 현금 예약,
포지션 생성 경쟁과 여러 잠금의 정렬 규칙이 복잡해진다.

### 계좌 행 하나를 먼저 잠그는 비관적 잠금

모든 주문 변경 트랜잭션이 `paper_accounts` 행을 먼저 `SELECT ... FOR UPDATE`한다.
같은 계좌의 주문은 직렬화되고 다른 사용자 계좌는 서로 막지 않는다.

## 최종 선택

모의투자 단계에서는 계좌 단위 비관적 잠금을 사용한다.

모든 변경 경로의 잠금 순서는 다음과 같다.

```text
paper_accounts
→ paper_orders (기존 주문을 변경할 때)
→ positions (체결 시 해당 종목)
```

- 신규 주문은 계좌를 잠근 뒤 멱등성 키를 확인하고 주문을 생성한다.
- 대기 주문 체결은 계좌를 잠근 뒤 대상 주문을 잠그고 포지션을 잠근다.
- 주문 취소도 계좌를 잠근 뒤 대상 주문만 잠근다.
- SQLAlchemy `with_for_update(of=...)`를 사용해 PostgreSQL의 잠금 대상 테이블을
  명시한다.
- 실행·종목 정보를 가져오는 outer join에는 `FOR UPDATE`를 적용하지 않는다.
- 최초 계좌 생성은 `(user_id)` 유일 제약과 `INSERT ... ON CONFLICT DO NOTHING`을
  사용하고, 초기 입금은 실제 계좌 삽입에 성공한 트랜잭션만 생성한다.
- 각 동시 요청은 별도 `AsyncSession`과 별도 트랜잭션을 사용한다.

## 선택한 이유

PostgreSQL의 `FOR UPDATE`는 같은 행을 잠그려는 다른 트랜잭션을 현재 트랜잭션이
끝날 때까지 기다리게 한다. 첫 번째 주문이 커밋되면 기다리던 두 번째 주문은 다음
SQL 문에서 변경된 원장과 포지션을 읽어 다시 검증한다. 현금 원장 전체를 직접
잠그는 대신 계좌 행을 동시 변경의 직렬화 지점으로 사용한다.

계좌 하나의 처리량은 낮아지지만 현재 모의투자에서는 정확성, 설명 가능성과
일관된 잠금 순서가 병렬 처리량보다 중요하다. PostgreSQL 공식 문서도 교착 상태를
줄이기 위해 여러 객체의 잠금을 일관된 순서로 획득할 것을 권고한다.

## 장점과 단점

장점:

- 동일 계좌의 현금·포지션 검증과 변경이 직렬화된다.
- 주문 생성, 대기 주문 체결과 취소가 하나의 잠금 규칙을 공유한다.
- 다른 사용자 계좌의 주문은 병렬로 처리할 수 있다.
- 잠금 대상과 순서가 명확해 교착 상태 분석이 단순하다.

단점:

- 같은 계좌의 서로 다른 종목·통화 주문도 동시에 처리하지 못한다.
- 오래 걸리는 트랜잭션 하나가 해당 계좌의 모든 주문을 지연시킨다.
- `READ COMMITTED`의 모든 이상 현상을 제거하는 일반 해법은 아니다. 안전성은 모든
  관련 쓰기 경로가 계좌 잠금 규약을 지킨다는 전제에 의존한다.
- PostgreSQL 전용 행 잠금 동작은 SQLite에서 검증할 수 없다.

## 나중에 설계를 변경해야 할 조건

- 계좌별 주문 처리량이 병목이 되면 통화별 현금 예약과 종목별 포지션 잠금을
  도입하고 전체 잠금 순서를 다시 정의한다.
- 여러 계좌를 한 트랜잭션에서 변경하게 되면 계좌 ID 정렬 순서로 잠그거나 더 강한
  격리 수준을 검토한다.
- `SERIALIZABLE`로 전환할 때는 serialization failure의 제한적 재시도와 멱등성
  검증을 함께 구현한다.
- 실제 증권사 네트워크 호출은 계좌 잠금을 보유한 채 수행하지 않고 outbox와
  대사 흐름으로 분리한다.
